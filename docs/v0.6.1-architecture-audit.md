# MechCAD v0.6.1 Architecture Audit

> 审计日期：2026-08-13
> 范围：只读架构审计。除本报告外未修改任何源代码；后端 142 项 unittest、前端 48 项 Vitest、`tsc --noEmit`、`npm run build` 均通过。

## 1. Executive Summary

MechCAD 已经具备一条“输入路由 -> 证据 -> 意图 -> FeaturePlanV3 -> 受控 CAD Worker -> 报告”的新架构主线，并且聊天编辑确实改成了 `FeatureEditSet` 特征级操作，能力层、过程时间线、快照/撤销/重做也都是真实实现。

核心结论：

- `FeaturePlanV3` 仍是 CAD Worker 唯一可执行输入，但“什么尺寸合法、什么特征可编辑、怎么排序、怎么补默认值”的知识至少分散在 5 个模块中，存在多份互相复制的维度表。
- 证据冲突只被记录进 `EvidenceSet.conflicts`，没有被校验、提问或阻塞，和 v0.6 宣称的“图文冲突必须提问并阻塞”不符。
- 几何验收只比较布尔运算前后的体积，无法证明孔径、孔位、槽深、阵列、壁厚正确。
- 参考体系仍是字符串（`origin/model_center/...`）加 `x/y/z` 数值，没有面、边、轴、基准等拓扑实体；Worker 也基本只在 Z 轴方向上做硬编码布尔运算。
- 能力层、模板层、规划层、校验层、Worker 层职责边界大体清晰，但“数据驱动扩展”目前只是部分实现，新增零件族仍需要动多处代码。

总体判断：这是一个“受控演示/概念级 CAD”架构，不是“可信参数化 CAD”架构。v0.7 应优先解决证据强制执行、拓扑参考、几何验收和维度知识收敛，而不是继续增加模板。

## 3. FeaturePlanV3

### 3.1 Schema

`backend/schemas.py:238` 定义 `FeaturePlanV3`，核心字段包括 `schema_version`、`part_family`、`autonomy_policy`、`design_intent_details`、`evidence`、`completeness`、`base_feature`、`features`、`assumptions`、`assumption_details`、`unresolved`、`design_review`、`self_checks`。

`FeatureV3`（`schemas.py:79`）包含 `id/type/operation/dimensions/placement/extent/pattern/depends_on/evidence/unresolved/assumptions/confirmed_by_user/execution_status`。其中：

- `type` 是自由字符串，不约束到已注册能力。
- `placement` 是 `PlacementV3`，`reference` 是自由字符串，`x/y/z` 是绝对数值，`axis` 只允许 X/Y/Z。
- `depends_on` 是字符串 ID 列表，没有实体、面、边、基准引用。
- `dimensions` 是 `dict[str, DimensionV3]`，每个维度带 `source/evidence/confidence/confirmed_by_user`。

### 3.2 Producers

| Producer | 文件/函数 | 类型 |
| --- | --- | --- |
| LLM 规划 | `backend/mechcad_ai/planner.py:generate_feature_plan` | LLM 驱动 |
| 本地模板规划 | `backend/generic_engine.py:build_template_plan` | 确定性 |
| 本地桩规划 | `backend/ai.py:_build_stub_feature_plan` | 确定性 |
| 智能自主补全 | `backend/ai.py:_apply_smart_autonomy`、`_complete_smart_feature`、`_add_full_autonomous_features` | 规则驱动，尺寸标记为 assumption |
| 聊天编辑 | `backend/ai.py:apply_feature_operations` | 基于 `FeatureEditSet` 的受控变更 |
| 属性编辑 | `backend/ai.py:patch_feature` | 基于 PATCH 的直接变更 |
| 澄清回答 | `backend/ai.py:apply_clarification_answers` | 受控合并 |
| 撤销/重做 | `backend/session.py:SessionStore` | 快照恢复 |

### 3.3 Consumers

Worker（`cad_worker/freecad_executor.py`）、校验（`backend/validation.py`）、能力校验（`backend/capabilities.py`）、问题生成（`backend/ai.py:questions_from_plan`）、前端特征树与属性面板、快照持久化、`ExecutionReport` 生成。

### 3.4 Source of Truth

结论：**FeaturePlanV3 是“执行层”的单一事实来源，但不是“能力/合法性/工程知识”的单一事实来源。**

Worker 只读取 `FeaturePlanV3`，这一点成立。但以下元数据互相重复：

- `backend/capabilities.py:_build_default_capabilities`：每个特征类型的可编辑参数。
- `backend/validation.py:_REQUIRED_DIMS`：每个特征类型的必需尺寸。
- `backend/ai.py:_required_dimensions` 与 `_refresh_smart_resolution`：又一份必需尺寸表。
- `backend/mechcad_ai/normalize.py:_FEATURE_KEY_ALIASES`：别名和尺寸键。
- `backend/generic_engine.py:feature_semantics`：必需/可选尺寸与几何效果。

这些表当前恰好一致，但没有任何机制保证它们一致。任何新增特征类型必须同时修改 4 到 6 处，否则会静默出现“能力允许但校验拒绝”或“校验通过但 Worker 跳过”的分叉。

## 4. FeatureEditSet

实际编辑链：

```text
用户意图
  -> planner.chat_edit_operations 或 _local_feature_edit
  -> FeatureEditSet
  -> validate_feature_edit_set / validate_feature_operation
  -> apply_feature_operations（按 add/update/delete/change_type 应用）
  -> order_feature_plan
  -> validate_feature_plan
  -> CAD Worker
  -> ProcessRecorder + DesignSnapshot
```

实现点：

- `backend/mechcad_ai/planner.py:85` 强制模型返回 `FeatureEditSet`；`normalize_feature_edit_set` 会拒绝带 `schema_version/base_feature/features` 的整份 plan。
- `backend/ai.py:280` `apply_feature_operations` 对 `deepcopy(plan)` 操作，逐操作生成 ProcessStep。
- `backend/ai.py:442` 删除父特征时，如果存在子依赖且未确认 `cascade`，会生成确认问题并记为 `blocked`。
- `backend/main.py:262` 聊天入口完整走上述链路。

绕过点：

- `backend/ai.py:815` `patch_feature` 不构造 `FeatureEditSet`，而是直接调用 `validate_feature_patch` 后原地修改 `FeatureV3`。它虽然走能力校验，但没有复用 `_apply_update_operation` 的完整语义、strict 过滤、`changed` 快照逻辑；`changed` 由 `main.py` 事后补录。这是 PARTIALLY IMPLEMENTED 的编辑统一。
- `apply_feature_operations` 在循环中对原 `plan` 做校验，新增特征之间不能互相依赖；同一 `edit_set` 中先 add 后 add 并 `depends_on` 前一个新增特征时，后一个依赖会判不存在。当前常见编辑不触发，但属于编辑架构限制。

## 5. FeatureCapability

`CapabilityRegistry` 是模块级单例，注册内容包括 3 种基体、3 种孔、槽/腔、外环槽、内环槽、`link_plate`、3 种加料、2 种阵列；`spur_gear` 以 `implementation_status="unsupported"` 注册。

结论：**能力层是无状态的静态元数据**，没有把运行时模型状态泄漏进去；`validate_feature_operation` 和 `validate_feature_patch` 都是纯函数，不修改 plan。

但需要指出：

- `reference_types` 对全部特征统一填 `_CENTERED_REFERENCES`，没有按特征类型区分，也没有校验 `reference` 是否真的对应某个已存在实体。它是元数据，但信息量很低。
- 能力层不是“唯一来源”。文档 `docs/capability_runtime.md` 声称 capability 是“single source of truth for editable parameters”，实际同一参数集合在 `validation._REQUIRED_DIMS`、`ai._required_dimensions`、`normalize._FEATURE_KEY_ALIASES` 中重复。这是 DOCUMENTATION / CODE MISMATCH。
- `counterbore_hole` 只声明 `diameter/depth`，Worker 也按普通圆柱孔执行，没有沉孔直径/沉孔深度；`linear_pattern/circular_pattern` 直接造孔，不引用被阵列的子特征。

## 6. generic_engine

`backend/generic_engine.py` 的职责分类：

| 分类 | 函数 |
| --- | --- |
| A. orchestration | `build_template_plan`、`fill_smart_defaults` |
| B. parsing | `extract_clues`、`_clue` |
| C. intent interpretation | `infer_design_intent` |
| D. template selection | `detect_family`、`FamilyTemplateRegistry` |
| E. feature generation | `_template_base`、`_template_features`、`_fill_smart_defaults`、`_smart_default` |
| F. placement/reference logic | `_placement_for_rule` |
| G. validation | 无独立校验；由 `validation.py` 负责 |
| H. evidence | `build_evidence_set`、`_iter_vision_evidence`、`_find_evidence_conflicts` |
| I. report | `_completeness`、`build_execution_report` |
| J. semantics | `feature_semantics` |

问题：

- `_placement_for_rule` 是 if/elif 硬编码的 placement rule 分发，不是模板数据驱动；新增一种放置规则必须改这个函数。
- `extract_clues` 与 `backend/ai.py:_extract_dimension_clues` 是两套维度解析正则，存在重复和结果差异风险。
- `infer_design_intent` 目前只是极简关键字判断，`function` 基本是 `mounting and connection` 或 `mechanical part`，没有真实受力/安装/连接推理。
- `feature_semantics` 只覆盖 8 种特征，而 capabilities 注册 15 种；语义表与能力表不一致，前端 `/api/capabilities` 会把两套数据都返回。

## 7. Template System

`FamilyTemplateRegistry` 是真实存在的数据注册表，`DEFAULT_TEMPLATES` 已注册 `flange`、`tube`、`link_plate`、`phone_stand`、`spur_gear`。

`build_template_plan` 会：

- 用 `detect_family` 判断零件族；
- 用 `_template_base` 生成基体；
- 用 `_template_features` 生成特征；
- Smart 模式调用 `_fill_smart_defaults`；
- 记录 unsupported requirements，例如 `spur_gear_teeth`。

结论：模板系统是 PARTIALLY IMPLEMENTED 的数据驱动。

- 新增“使用现有特征类型和现有 placement rule”的零件族只需加 `FamilyTemplate`，这是真的。
- 新增“需要新尺寸词汇、新放置规则、新特征类型”的零件族，仍需修改 `extract_clues`、`_placement_for_rule`、capabilities、validation、normalize、Worker。文档 `docs/generic_engine.md` 说“No changes to planning orchestration, validation, the CAD Worker, or UI are required”，只在受限条件下成立。
- `spur_gear` 模板只生成“齿轮毛坯+中心孔+轮毂”，齿形明确不支持，行为诚实。

## 8. Evidence / Completeness / Self-Check

- `EvidenceSet` 有 `input_kind/items/conflicts`，`build_evidence_set` 会把文字线索标记为 `source=user, confirmed_by_user=true`，把视觉 JSON 标记为 `source=drawing`。
- 冲突检测 `_find_evidence_conflicts` 只在“同 key 且数值不同”时记录。
- **冲突没有被消费**：`validate_feature_plan`、`_execution_gate`、前端 TaskPane 都不读取 `evidence.conflicts`；前端虽然把 `evidenceConflicts` 传给 TaskPane，但渲染层没有使用。用户输入与视觉读图矛盾时，系统仍可能继续建模。这是 v0.6 明确要求但未完成的能力。
- `self_checks` 由 `validate_feature_plan` 写入 plan，包含 `engine/mode/order/checks/summary`；`checks[]` 是结构化 `{id, feature_id, status, message}`。前端 Review 页会展示。
- `validate_feature_plan` 和 `FeaturePlanV3.model_validator` 都是“有副作用的校验”：会修改 `self_checks`、`design_review`、`unresolved`、`assumptions`、`assumption_details`。这给幂等性带来风险，例如同一 plan 被重复 validate 时 review 前缀 `[validation]` 依赖去重逻辑才能不无限追加。
- `_completeness` 的 `production_ready` 只看“modeled == total 且 unresolved == 0”，不检查几何真实尺寸；`build_execution_report` 的 `production_ready` 另外要求 strict 模式或无 assumptions。两处口径不同。

## 9. CAD Worker

`cad_worker/freecad_executor.py` 实际使用 Build123d，受控执行，不执行任意 Python。

已实现：

- 基体：`box_base`、`cylinder_base`、`hollow_cylinder`、`link_plate`。
- 特征：三种孔、矩形槽/腔、外环槽、内环槽、`boss_cylinder`、`rectangular_pad`、`rib_box`、线性和圆周阵列。
- 每个特征执行前后记录体积，体积不变且声称 modeled 时改判 `failed`。
- 写出 `process_steps.jsonl` 和 `execution_report.json`；超时、异常、跳过原因都进入日志和报告。
- 失败时 `backend/cad.py:_remove_failed_model_artifacts` 清理 STEP/STL/OBJ。

关键限制：

- 几何验收只比较体积。一个孔径错误、位置错误、阵列数量错误但体积发生变化的特征仍会被标记 `modeled`。
- 只支持 Z 轴特征；`axis != Z` 直接 skip，但 validation 不把非 Z 轴视为 block，严格模式也可能放行到 Worker 再跳过。
- `counterbore_hole` 与 `blind_hole` 执行逻辑几乎一样，没有真正的沉孔。
- `rectangular_slot` 与 `rectangular_pocket` 执行逻辑一样，`through` 只是普通深度参数。
- 阵列不引用种子特征。`circular_pattern` 直接用自己的 `diameter/count/pitch_radius` 生成多个减料圆柱；修改 `bolt_hole_seed` 不会自动影响阵列。
- 贯穿孔深度 `_through_depth` 基于基体 `length/height + 2`，对加料面、凸台上的孔可能切得过深。
- `MECHCAD_CAD_ENGINE` 环境变量只改变日志文案；Worker 永远跑 Build123d。若设置成 `freecad`，日志可能误导，但 `ExecutionReport.engine` 最终来自 Worker 报告的 `build123d`，前端展示仍正确。

## 10. Reference & Dependency System

- 引用是字符串：`origin/main_axis/center/flange_center/model_center/bottom_center/bottom_end_center/base_center/top_center/needs_position`。
- `PlacementV3.reference` 没有绑定到具体实体、面、边或轴；Worker `_placement` 直接取 `x/y/z`，多数情况下 `reference` 只是文档性字段。
- `depends_on` 用于拓扑排序和父删除保护，但 Worker 不读取依赖来做几何引用（阵列除外也仅靠 ID 排序）。
- 没有“父特征修改后子特征自动重算”的机制：整棵树每次从头 BuildPart 重放，子特征定位值如果依赖父特征尺寸，需要 AI 或模板重新计算，而不是 CAD 参数约束。
- `axis` 字段支持 X/Y/Z，但 Worker 只支持 Z；没有旋转角度、工作平面或草图平面概念。

## 11. Topological Naming Risk

- Feature ID 在快照中稳定，undo/redo 可以恢复同一份 plan。
- 但模型没有拓扑命名：没有 `Face/Edge/Vertex` ID，没有“上表面”“右端面”“某孔壁”的稳定引用；`fillet/chamfer` 因此无法执行（Worker 直接 skip）。
- 每次重建都是从 `FeaturePlanV3` 重新 BuildPart，几何完全重来；如果后续引入依赖父特征几何的编辑（例如“在凸台顶面开孔”），当前模型没有承载它的命名空间。
- 依赖删除保护只检查 `depends_on` 字符串；如果依赖引用丢失或改名，校验能发现，但无法自动修复。

## 12. Process / Snapshot / Undo / Redo

- `ProcessRecorder` 记录 upload/vision/planning/validation/chat_edit/cad/export 步骤，并支持 WS 发布；`generate`、`chat`、`patch` 都接入。
- `DesignSnapshot` 包含 feature_plan、artifacts、questions、design_review、execution_report、report_markdown、logs、process；`SessionStore.commit_snapshot` 深拷贝并写 JSON 持久化。
- undo/redo 恢复完整快照，因此 artifacts、process、report 一起恢复。
- 风险点：
  - `_refresh_restored_validation` 只重跑 `validate_feature_plan`，不重建 CAD；如果未来 CAD 引擎、库版本或默认值变化，旧快照的几何可能与新校验结果不一致。
  - `_refresh_restored_validation` 硬编码 `language="zh"`，恢复时会覆盖 plan 中的中/英文 self_checks。
  - `SessionStore._load` 在遇到 JSON 损坏时静默清空全部项目，没有备份或恢复策略。

## 13. Frontend Architecture

- 前端不是 CAD 状态源。`ProjectState` 由后端 API 响应写入，Zustand 只保存 UI、设置草稿、本地描述、图片文件和过程事件缓存。
- 描述与图片只在 `generate` 时传给后端，后端快照不保存原始图片；重新打开项目后，前端描述/图片不会自动恢复。
- WebSocket 消费 `process_step_*` 事件并更新过程时间线；普通 stage 事件写入日志。
- 特征树 `FeatureTree.tsx` 从 `plan.base_feature + plan.features` 派生，按基体/减料/加料/阵列/修饰分组，展示 status、missing、assumption 徽标和依赖缩进。
- 属性面板 `FeatureForm.tsx` 直接编辑 dimensions/placement，保存后走 `PATCH /features/{id}`；能力错误以 422 结构化 issue 返回。
- Review/Process/Export 面板都从快照派生，显示四维报告、自检项、过程步骤和 STEP/STL/OBJ 链接。
- 前端没有独立维护 evidence 或 CAD 几何；这一点是正确的架构方向。
- 小问题：`App.tsx:528` 的 `engineLabel` 在存在 plan 时固定显示 “Build123d Worker”，没有读取 `execution_report.engine`；当前 Worker 一致，但一旦真切换 FreeCAD，需要同步修改。`evidenceConflicts` 被传入但没有渲染。

## 16. Single Source of Truth

```text
USER INTENT
  -> description/image + clarification answers
FEATURE PLAN
  -> FeaturePlanV3
CAD GEOMETRY
  -> Build123d Worker
VERIFICATION
  -> validate_feature_plan + volume delta + ExecutionReport
EXPORT
  -> STEP/STL/OBJ artifacts
```

权威状态：

- 可执行设计：`FeaturePlanV3`。
- CAD 几何：Worker 生成的 solid，落盘为 STEP/STL/OBJ。
- 用户确认值：`DimensionV3.confirmed_by_user`、`FeatureEditOperation.confirmed_by_user`。
- 项目历史：`SessionStore` 的 `current/history/redo_stack`。

派生状态：

- `ExecutionReport`：由 plan + worker_report 派生。
- 前端特征树、过程时间线、Review 面板：由 ProjectState 派生。
- `assumption_details`：由 feature dimensions 派生并同步。

缓存状态：

- `frontend/dist`（构建产物）。
- `work/projects.json`（持久化缓存）。
- `work/new_arch_runs/`（运行产物）。

重复状态：

- 维度必需表：capabilities / validation / ai / normalize / feature_semantics。
- 家族判断：generic_engine.detect_family / ai._detect_family。
- 尺寸解析：generic_engine.extract_clues / ai._extract_dimension_clues。
- 零件族模板：`DEFAULT_TEMPLATES` 与 `ai._build_stub_feature_plan` 的 plate/flange/tube 分支。
- 放置规则：`_CENTERED_PLACEMENTS` 在 schemas 相关常量、validation、capabilities、worker 中重复。

模糊状态：

- `evidence.conflicts`：记录但无人消费。
- `FeatureV3.pattern`：schema 有字段，Worker/编辑链基本不使用。
- `PlacementV3.reference`：语义不明确，Worker 只读 x/y/z。
- `MECHCAD_CAD_ENGINE`：名称像引擎开关，实际只是日志标签。
- `mechcad/` 与 `legacy/gradio/mechcad/`：两处旧代码，README 只说明后者。

## 18. P0 Findings

P0-1 证据冲突收集了但没有强制执行。`backend/generic_engine.py:106` 把冲突写入 `EvidenceSet.conflicts`，但没有任何校验、提问或阻塞消费者；前端也未展示。这违反了 v0.6 的“图文冲突必须提问并阻塞”。

P0-2 几何验收不能证明模型正确。`cad_worker/freecad_executor.py:147` 只比较执行前后体积；孔径、位置、阵列、槽深、壁厚错误仍可能被标记 `modeled`。`geometry_valid` 名不副实。

P0-3 参考与依赖不是拓扑系统。`PlacementV3.reference` 是字符串，`depends_on` 不驱动几何；Worker 只使用 x/y/z，且阵列不引用种子特征。任何“基于实体/面的参数化编辑”都无法安全实现。

P0-4 同一份能力/维度知识至少重复 5 份。capabilities、validation、ai、normalize、feature_semantics 各有一份，新增特征类型必须同步多处分叉；这是未来不一致和静默错误的根因。

## 19. P1 Findings

P1-1 `patch_feature` 绕过完整 `FeatureEditSet` 编辑链，直接改 FeatureV3；虽然经过 `validate_feature_patch`，但没有复用 `_apply_update_operation` 的统一语义。

P1-2 Worker 只支持 Z 轴，但校验不把非 Z 轴设为 block，结果是严格模式也可能把特征放到 Worker 再 skip，用户体验为“检查通过但建模失败”。

P1-3 提示词允许 `revolved_axial_profile/fillet/chamfer`，能力注册表与 Worker 不支持；`prompts/prompts.yaml` 的 `design_review` 提示词从未被调用。

P1-4 `MECHCAD_CAD_ENGINE` 只是日志标签，不是引擎开关；文件名 `freecad_executor.py` 会误导审计者。

P1-5 `full_autonomous` 仍是规则驱动，只对 tube、support 等关键词增加少量特征，不满足“全自主方案设计”。

P1-6 `_placement_for_rule` 是硬编码 if/elif，模板数据驱动的“新增零件族只改配置”声明被高估。

P1-7 数组/槽/沉孔语义简化：counterbore 无沉孔深度，slot/pocket 无真实 through，pattern 不引用种子特征。

P1-8 undo/redo 只重跑校验，不重建 CAD；`_refresh_restored_validation` 硬编码中文。

P1-9 `mechcad/` 根目录旧代码仍存在且测试仍引用；README/审计者容易混淆。

P1-10 `questions_from_plan` 在 `backend/ai.py` 中定义两次，存在死代码。

## 20. Recommended Architectural Invariants

1. `FeaturePlanV3` 始终是唯一可执行设计源，任何编辑必须先生成新 plan 再执行 Worker。
2. 能力、必需尺寸、别名、语义、Worker 支持集必须来自同一份注册表，禁止各模块独立维护维度表。
3. 证据冲突必须成为可阻塞的输入状态：检测、展示、提问，未解决前不能进入 CAD。
4. Worker 只能报告真实几何结果；没有尺寸/位置/布尔结果验证时，不得输出 `geometry_valid=true`。
5. 新增特征类型必须同时登记 capability、semantics、validation、Worker executor；任何缺失都视为未注册，不允许静默 skip 或静默 drop。
6. 所有编辑入口（生成、聊天、属性、撤销/重做）必须走同一套 validate -> apply -> order -> gate -> CAD 流程。
7. 参考体系必须从字符串升级为稳定实体引用（面/边/轴/基准），且依赖必须驱动几何，而不是只用于排序。
8. UI 永不成为 CAD 状态源；描述、图片、设置草稿可以在前端，但可执行事实只能来自后端快照。
9. 快照恢复时，如果 plan 或引擎元数据变化，必须重新执行 CAD 或明确标记产物为 stale，不能静默复用旧 artifacts。
10. 文档中宣称的能力必须以代码注册表和测试为准；不支持的能力要在 prompt、capability、validation、UI 四处一致显示为 unsupported。
