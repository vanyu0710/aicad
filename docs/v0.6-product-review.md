# MechCAD v0.6 Product Review and Improvement Roadmap

Date: 2026-08-13
Branch: `codex/mechcad-pro-ui`
Scope: generic modeling core, UI acceptance layer, and the path to a production-usable AI CAD IDE.

## Executive Summary

MechCAD has moved from an AI-script demo to a controlled parametric CAD prototype. The strongest part is execution trust: FeaturePlanV3 is the only executable truth, the CAD Worker is isolated and auditable, and failed geometry is reported instead of silently ignored. The weakest part is not export, but engineering interpretation: image understanding, geometry verification, reference handling, and autonomous design are not yet production-grade.

## Verified Capability Today

- Text-driven parts for flange, tube with internal groove, rocker/link plate, and phone stand are generated through the generic engine and modeled by the Build123d Worker.
- Each supported probe produced STEP, STL, and OBJ artifacts.
- Strict mode keeps missing dimensions unresolved and blocks execution; Smart mode fills auditable assumptions and marks `production_ready=false`.
- Spur gear teeth are explicitly unsupported and never faked.
- Feature-tree grouping, capability registry, process timeline, undo/redo, and Chinese/English settings are in place.

## Current Strengths

- Single source of truth: `FeaturePlanV3` is validated before planning, chat edits, feature patches, and CAD execution.
- Controlled execution: the Worker subprocess has timeout handling, real error propagation, and per-feature execution status.
- Generic pipeline skeleton: input routing, evidence set, design intent, family templates, feature semantics, completeness, and four-dimensional execution report.
- Productized UI shell: startup page, manager panes, 3D-centered layout, settings center, and mode switching.
- Failure honesty: unsupported capabilities and geometry that did not change are no longer reported as successful models.

## Critical Gaps

### 1. "Generic" is still data-driven templates, not a general modeling kernel

Adding a new part family works when it uses existing base types, feature types, dimension vocabulary, and placement rules. New reference relationships, sketch profiles, fillets/chamfers, mirrors, or feature families still require changes to the parser, capability registry, placement logic, and Worker mapping.

### 2. Geometry acceptance is too shallow

The current acceptance check mainly verifies whether solid volume changes. This catches empty booleans and non-intersecting cuts, but does not prove that hole diameters, hole positions, groove geometry, pattern counts, or pattern directions are correct. A part can be marked `modeled` and still be wrong.

### 3. Image-to-model evidence loop is incomplete

Image input is routed to a vision model, but there is no robust engineering evidence chain: dimension line coordinates, view relationships, scale inference, feature candidates, and text/image conflicts are not yet resolved and confirmed visually.

### 4. Smart mode is autonomous filling, not engineering design

Smart mode can complete dimensions and combine templates. It does not yet generate multiple explainable solutions from load, assembly, material, manufacturing method, standard parts, or wall-thickness rules, nor let the user compare and confirm a design intent.

### 5. Review UX is not enough for professional CAD

The UI has the right shell, but users still cannot inspect a model the way CAD demands: section views, measurements, standard views, feature highlight, single-feature isolation, transparency, and dimension annotations.

## Roadmap

### P0: Geometry Acceptance Kernel

- Define expected geometry effects per feature semantics: volume delta, bounding-box change, face/axis count, hole diameter, position, pattern count, and direction.
- After Worker execution, inspect the real BRep with OpenCascade/Build123d instead of only comparing volume.
- Report per-feature `pass`, `deviation`, or `failed` with measured versus expected values.
- Keep old STEP/STL/OBJ only when geometry acceptance passes or is explicitly marked as a concept preview.

### P1: Reference and Feature Semantics Engine

- Introduce safe reference resolution for faces, axes, edges, datums, and feature centers instead of growing `placement_rule` branches.
- Move template placement and dimension mapping to declarative constraints.
- Add high-frequency feature types: sketch profile, extrude, revolve, hole wizard, fillet, chamfer, rib, mirror, linear/circular pattern.
- New feature types should require only a capability entry plus Worker mapping, not pipeline rewrites.

### P2: Drawing Evidence Pipeline

- Vision output should include dimensions, dimension-line coordinates, view labels, confidence, and feature candidates.
- Text/image conflicts must be shown to the user and resolved before execution.
- Clarification questions should reference the visible drawing region and the currently known dimensions.

### P3: Professional Review UI

- Add section views, measure, standard views, feature highlight, feature isolation, and transparency.
- Feature-tree selection should highlight actual geometry.
- Reports should separate confirmed dimensions, AI assumptions, unresolved questions, geometry acceptance, and manufacturing risks.

### P4: Smart Solution Generation

- Smart mode should first produce design goals, constraints, solution candidates, and assumptions.
- `full_autonomous` remains concept-only unless evidence, geometry acceptance, and manufacturing checks pass.
- Production-ready must never be inferred from a successful export.

## Acceptance Criteria for the Next Version

- A new part family using only registered capabilities can be added through template configuration without touching planning, validation, Worker, or UI code.
- A new feature type requires one capability entry and one Worker mapping, and both are covered by tests.
- Strict mode never executes unconfirmed inferred dimensions.
- Smart mode assumptions are visible in the feature tree, report, and execution log.
- Geometry acceptance verifies actual dimensions and positions, not only volume.
- Image conflicts block execution until the user confirms the correct interpretation.

## Recommended Focus

Do not add more part templates first. Invest in P0 geometry acceptance and P1 reference/feature semantics. These two layers convert MechCAD from a collection of working examples into a genuinely extensible CAD core.
